### B-01 · Free catches are counted more than once by the database

| Severity | Confidence | Area | Gate | Task |
|---|---|---|---|---|
| Critical | Reproduced | Database trigger × app collection store | Before testers | T-266 |

**Where.**
- `supabase/migrations/20261029000001_free_catch_enforcement.sql`: function
  `public.enforce_free_catch()` lines 46–94; trigger `collection_enforce_free_catch` lines 99–102
  (`before insert or update of caught_at … for each row`).
- `lib/supabaseCollectionStore.ts:129-135` (`upsertOne`: `.upsert(row, { onConflict:
  'user_id,species_id' })`) and `:93-102` (`apply`: read the row, apply the change, upsert the
  whole row).
- `lib/offlineCollectionStore.ts:111-133` (every `markSpotted` / `markCaught` / `markHelped`
  queues a write, including when nothing changes) and `:160-170` (handling of a refused write).
- `pipeline/db/verify.py:138-151` (the live checks for this rule).

**Now.**
1. Every collection write the app sends is an upsert of the full row. Postgres runs the
   `BEFORE INSERT` row trigger for an upsert even when the row already exists, and then, on the
   conflict, the `BEFORE UPDATE` row trigger as well.
2. In the `INSERT` firing, `tg_op` is `'INSERT'`, so the branch that recognises an unchanged or
   already-counted row (line 65, `if tg_op = 'UPDATE' and old.caught_at is not null`) is skipped.
   If `new.caught_at` is not null the function counts one catch.
3. In the `UPDATE` firing that follows, if the stored row had `caught_at` null, the function
   counts a second catch.
4. Result, measured (Appendix A): for a free user, catching a species that already has a
   Spotted row raises `profiles.free_catches_used` by **2**. Any later upsert of a row whose
   `caught_at` is set — a help pledge on it, or tapping it again in This Week — raises it by
   **1**. When the counter is 3, every upsert of a row whose `caught_at` is set fails with
   `free_catch_limit`, including the first catch of a different species. In the reproduction,
   one catch followed by one pledge on it was enough for the user's second real catch to be
   refused.
5. The app computes "free catches left" from its local records (`lib/freeCatch.ts:64-74`), one
   per caught species this season, so it disagrees with the server from the first catch.
6. When the server refuses a write, the app removes the catch from the local record
   (`uncatch`, `offlineCollectionStore.ts:196-199`) whatever kind of write was refused, and
   shows nothing.

**Should.** A free user gets exactly 3 catches per season; a catch is counted once; re-saving an
unchanged row and re-catching within the same season cost nothing. Sources: the migration's own
comment (lines 55–59), `FREE_CATCHES_PER_SEASON = 3` in `lib/freeCatch.ts:11`, GDD §4 ("Free
taste: 3 catches per season"), string `paywall.body`.

**See it.** Appendix A. In the app: as a free user, tap a species in This Week, open its card,
complete a catch; then catch a second species the same way. The second catch shows "You
caught …!" and disappears from the Almanac after the next sync.

**Affected.** Every free user who catches a species they have already spotted, which is the
normal path (This Week tap → card → catch). Full Game owners are not affected (the function
returns at line 81 before counting).

**Change.**
1. In `enforce_free_catch()`, when `tg_op = 'INSERT'` and a row for `(new.user_id,
   new.species_id)` already exists, return `new` without counting; the `UPDATE` firing then
   decides with `old` available.
2. Add checks to `pipeline/db/verify.py` that use the exact upsert statement in Appendix A.
3. In `OfflineCollectionStore`, do not queue or send a write when the transition leaves the
   record unchanged.
4. In `OfflineCollectionStore.drain`, call `uncatch` only when the refused operation has
   `kind === 'caught'`.
5. After deploying, set `free_catches_used` for the current season to the number of rows with
   `caught_at` in the current season, per user.

**Done when.**
- With the upsert statement of Appendix A, `free_catches_used` is: 0 after an upsert with
  `caught_at` null; 1 after the first upsert with `caught_at` set, whether or not the row
  existed; unchanged after re-sending the same row; unchanged after an upsert that only adds
  `helped_at`.
- A fourth distinct species caught in one season by a free user is refused; the first three are
  accepted.
- `verify.py` fails if any of the above is false.
- Tapping an already-spotted species sends no request to `collection`.
- A refused `spotted` or `helped` write does not change `caughtAt` on the device.

### B-02 · The webhook ignores every RevenueCat TRANSFER event

| Severity | Confidence | Area | Gate | Task |
|---|---|---|---|---|
| Critical | Vendor docs | RevenueCat webhook | Before testers | T-267 |

**Where.** `lib/revenuecatEvents.ts:77` (returns `ignore` when `entitlement_ids` is not an
array), which runs before the TRANSFER branch at `:95-98`. The generated copy
`supabase/functions/_shared/lib/revenuecatEvents.js` is what the Edge Function runs. Test:
`lib/revenuecatEvents.test.ts:51-59`.

**Now.** For an event of type `TRANSFER`, RevenueCat sends `transferred_from`,
`transferred_to` and common fields only (Appendix B). `ev.entitlement_ids` is therefore
undefined, line 77 returns `{ kind: 'ignore', reason: 'no entitlement list' }`, the Edge
Function answers HTTP 200, and no entitlement row changes. The unit test passes because it
builds its TRANSFER event from a purchase fixture that includes `entitlement_ids` and
`product_id`.

**Should.** On TRANSFER, the entitlements of the source accounts are revoked and granted to the
destination account. Sources: the comment at `lib/revenuecatEvents.ts:95-101`, T-217 ("TRANSFER
revokes from the old account and grants to the new one"), T-086 ("New anonymous account after a
reinstall: RevenueCat sends a TRANSFER, and the webhook revokes … and grants"), privacy policy
("you can restore the purchase into a new account").

**Change.** Each data-pipeline run writes a fixed-size random sample (for example 30 species ×
the 5 most used languages) to a review file in the run artifacts, with the honesty check
results; the Director or a native reader marks each as correct or not; the error rate is
recorded in the task plan.
**Done when.** The sample file is produced by the workflow, and one review has been recorded
with its error rate.
**Effort.** S.

#### I-34 · Refresh presence before spring as well

**Problem today.** The data pipeline runs once a year, on 5 February
(`.github/workflows/data-pipeline.yml:28`). Observations from spring and summer arrive in GBIF
months later; a yearly refresh in February is fine for counts but leaves new species out for a
year.
**Change.** Keep the February run and add one in late August, before autumn migration.
**Done when.** The workflow has two schedules and the load guard (`gbif/load_guard.py`) passes
on both.
**Effort.** XS.

#### I-35 · Sweden's own Red List beside the global one

**Problem today.** The card shows the IUCN category worldwide (`20261113000002…sql`, T-263). A
species can be Least Concern globally and threatened in Sweden (and the reverse).
**Change.** Load the Swedish Red List category (Artdatabanken / SLU) for catalogue species,
after checking its licence permits this use (DATA-SOURCING-LICENSING.md decision), and show
both, each labelled with its scope.
**Done when.** The licensing doc records the decision; if permitted, a `species.redlist_se`
column exists and the card labels both lines.
**Effort.** S (plus the licence check).

#### F-01 · "Protected" and "invasive" marks on the card

**Need.** The Helped tier is about not harming species, but the card does not say which species
the law protects or which are invasive. A user can pick a protected orchid while reading its
card, or admire an invasive lupin.
**Behaviour.** Under the name, one of: "Protected in Sweden: do not pick, dig up or disturb"
(with the legal scope in one line), or "Invasive in Sweden: do not plant or spread it" with a
link "Report where you saw it". The pledge buttons on an invasive species say "Pledge not to
spread it" instead of the generic give text.
**Data.** Protected: the species listed in the Swedish Species Protection Ordinance
(*Artskyddsförordningen*, SFS 2007:845, annex 1 and the county-level protections in annex 2).
Invasive: the EU list of invasive alien species of Union concern (Regulation (EU) 1143/2014 and
its implementing lists) and Sweden's national list. Both are legal texts, free to use; the
mapping to catalogue ids is a one-off manual table (`pipeline/data/legal_status.csv`) of a few
hundred rows, re-checked yearly. The reporting link is the responsible authority's page; the
Director confirms the current URL.
**Cost.** None to run.
**Invariants.** #1 (the mark states a legal status, not presence); #2 (free for every species);
#5 (supports safety).
**Done when.** `species.legal_status` (`protected` / `invasive` / null) is loaded from the table;
the card shows the line for every species with a status; a test checks one protected and one
invasive species; the table's source and date are recorded in DATA-SOURCING-LICENSING.md.
**Effort.** S.

#### F-02 · Arriving soon / leaving soon

**Need.** "Active this season" changes slowly; users have no weekly reason to open the app in
autumn and winter (P-06).
**Behaviour.** Two short lists at the top of This Week: "Arriving in {county}" — species whose
records in the next month are at least 3 times this month's and at least 20; "Leaving soon" —
species whose next-month records are below a quarter of this month's. At most 5 each, named and
with photos, never worded as "here now".
**Data.** `species_presence.month_counts` (T-261), already loaded.
**Cost.** None beyond B-20's cache.
**Invariants.** #1: copy reads "usually arrives in {county} in {month}", from records.
**Done when.** The lists are computed by a pure, tested function from monthly counts; they are
empty rather than padded when no species qualifies; the honesty test covers their strings.
**Effort.** S. **Depends on.** B-04 and B-65 (otherwise the counts are wrong).

#### F-03 · Notification choices

**Need.** One notification a day at an hour derived from the user id (`lib/sendSlot.ts`) is the
only option. USER-FLOWS §9 shows "Cadence: gentle / daily", "Quiet hours" and a "Good time now"
toggle in Settings; TSD §4 lists `notif_prefs` and `quiet_hours`. None is built.
**Behaviour.** In Settings → Notifications: frequency (daily / 3 a week / weekly), a preferred
window (morning 8–11 / midday 11–15 / evening 15–21), and groups to include (birds, mammals,
insects, plants, other). Stored server-side on `profiles` (a new `notif_prefs jsonb`), read by
the sender.
**Data.** User input.
**Cost.** None.
**Invariants.** #6 (consent stays the master switch); quiet hours 21–08 stay fixed.
**Done when.** `planSends` honours each setting (unit tests for each); the Settings screen
writes them; defaults equal today's behaviour.
**Effort.** M.

#### F-04 · Weekly recap notification
