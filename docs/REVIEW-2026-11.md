## 3. Launch blockers

### B-01 · Free catches are miscounted by the database — *Critical · Reproduced*

**Where:** `supabase/migrations/20261029000001_free_catch_enforcement.sql` (trigger
`collection_enforce_free_catch`, line 101; function body lines 60–93) together with
`lib/supabaseCollectionStore.ts:132` (`.upsert(row, { onConflict: 'user_id,species_id' })`).

**Cause.** The trigger is `BEFORE INSERT OR UPDATE OF caught_at`. A PostgREST upsert is
`INSERT … ON CONFLICT DO UPDATE`, and Postgres fires `BEFORE INSERT` row triggers for the proposed
row **even when the row already exists**, then fires `BEFORE UPDATE` as well. The function only
recognises "an unchanged row being re-saved" in its `UPDATE` branch (line 65). In the `INSERT`
firing it sees `caught_at` set and counts a new catch every time.

**Reproduction** (the repository's two migrations, unmodified, with PostgREST-shaped upserts):

| Step (what the app does) | `free_catches_used` after |
|---|---|
| Tap a species in This Week (spotted) | – |
| Catch it — the first real catch | **2** |
| Pledge help on it | **3** |
| Tap it again in This Week | `ERROR: free_catch_limit` |

**What a user sees.**
- Spot-then-catch (the normal path: This Week → card → catch) costs two of the three catches.
- The second catch of another spotted species pushes the count to 3 in the `INSERT` firing and is
  then refused in the `UPDATE` firing. The app has already shown "You caught …!". On sync the
  outbox un-catches it (`lib/offlineCollectionStore.ts:163-169`) with no message.
- Every later write to a caught species counts too: a help pledge, and a simple re-tap in This
  Week, because `markSpotted` always writes and the store always upserts the full row.
- The app's own counter is derived from local records, so it shows "2 free catches left" while
  the server has none. The sales funnel then measures a paywall most people never legitimately
  reach, or reach for the wrong reason.
- Full Game owners are unaffected (the trigger returns before counting).

**Why the checks missed it.** `pipeline/db/verify.py:146-151` proves "a PostgREST upsert … must
not count as a catch" with a plain `UPDATE`, and catches 1–4 with plain `INSERT`s. Neither is the
statement the app sends.

**Fix.**
1. In the function, when `tg_op = 'INSERT'` and a row for `(user_id, species_id)` already exists,
   `return new` and let the `UPDATE` firing judge it with `old` in hand.
2. Add upsert-shaped steps to `verify.py`, and run the SQL rules in CI against a real Postgres
   (see I-14) so this class of bug cannot return.
3. Client: skip the write when a transition changes nothing (`applySpotted` on a spotted row), and
   only un-catch when the refused operation was a catch.
4. Reset `profiles.free_catches_used` for the current season once the fix is live.
5. Tell the user when the server refuses a catch (B-13).

### B-02 · Restore purchases does nothing across accounts — *Critical · Vendor docs*

**Where:** `lib/revenuecatEvents.ts:77`, reached before the TRANSFER branch at line 95.

RevenueCat's field reference lists, for `TRANSFER`, only the common fields plus
`transferred_from`, `transferred_to` and optional `store`, `environment`,
`subscriber_attributes`. There is no `entitlement_ids`, `product_id` or `app_user_id`. Line 77
returns `ignore: 'no entitlement list'` for every real TRANSFER.

The unit test (`lib/revenuecatEvents.test.ts:51`) builds its TRANSFER from the purchase-shaped
fixture, which does carry `entitlement_ids`, so it passes.

**Effect.** Buy → reinstall (new anonymous account) → Restore: RevenueCat moves the purchase,
our database never hears what moved, the user stays locked. T-086's closing scenario and the
privacy policy's "you can restore the purchase into a new account" both depend on this.

**Fix.** On TRANSFER, move the rows in SQL: a `transfer_entitlements(from uuid[], to uuid[], at,
event)` function that deactivates every active row of the `from` accounts and grants the same
entitlements to `to`, then refreshes `full_game` for both and for household members. No
RevenueCat API call is needed.

### B-03 · County packs and All of Sweden are never granted — *Critical · Vendor docs*

**Where:** same line 77, with `docs/launch/PAYMENTS-SETUP.md` Part G ("the county packs and
`all_regions` need **no** entitlements").

RevenueCat documents `entitlement_ids` as "`null` if the `product_id` is not mapped to any
entitlements". `Array.isArray(null)` is false, so the event is ignored one line before
`productEntitlement()` is consulted (line 78) to recognise the product. The tests use
`entitlement_ids: []` (lines 120, 125), which RevenueCat does not send.

**Effect.** 22 of the 24 products take money and unlock nothing.

**Fix.** Treat a missing or null list as empty; require only that the list *or* the product id
yields a known entitlement. Add tests with `entitlement_ids: null` and with the field absent.
Before launch, capture one real sandbox payload per event type and keep them as fixtures.

### B-04 · "Active this season" is not seasonal — *Critical for invariant #1 · Measured*

**Where:** `pipeline/gbif/aggregate.py:28` (`entry["months"].add(month)` for any record),
consumed by `lib/presence.ts`, `lib/thisWeekProduction.ts:46-58` and the notification sender.

`active_months` is every month that has at least one GBIF record in any year. With hundreds of
thousands of records per county, strays, misdated records and overwintering individuals fill the
calendar. In the committed data:

| Group | County rows with ≥ 1,000 records | of which "active" all 12 months |
|-------|------:|------:|
| Birds | 4,558 | 2,970 (65 %) |
| Mammals | 166 | 129 (78 %) |
| Flora | 5,760 | 2,268 (39 %) |
| Molluscs | 82 | 36 (44 %) |
| Amphibians | 30 | 12 (40 %) |

Kronoberg examples, all `[1..12]`: common swift, barn swallow, cuckoo, osprey, crane. Lily of the
valley is "active" in December and January.

**Effect.**
- This Week filters on `active_months` and sorts by **all-year** occurrences, so in winter the top
  of the list is the year's most-recorded species, summer migrants included, under the subtitle
  "species active in your area this season".
- The sender uses the same gate and can push "Barn Swallow is active in your region — This is its
  season where you live" in January.
- The Almanac's "active this month" filter and the season chips are equally loose.

**Fix.** The monthly counts already exist since T-261 (`month_counts`), and
`lib/countyStats.ts` already has the right rule (`PRESENT_SHARE`: a month counts from 5 % of the
busiest month). Use it everywhere: derive `active_months` in the pipeline from the monthly counts
with that threshold and a minimum count, rank This Week by **this month's** records, and weight
notifications by them. Add a data test: no summer migrant on a fixed list is active in January.

### B-05 · Account deletion leaves the collection on the device — *High · Read*

**Where:** `App.tsx:663-688`.

`confirmDeleteAccount` clears onboarding, hometown, entitlements, travel log, quiz attempts and
recognised species. It does not clear `nearby.collection.v1` (the offline collection cache and
outbox), and `OfflineCollectionStore` has no `clear()`. `useCollection` keeps the old records in
memory too.

**Effect.** After "Delete permanently" the app returns to onboarding with every sighting, catch
and pledge still shown. The comment at line 676 says the opposite: "the next person to open the
app starts fresh". The stale catches also count against the new account's free catches on the
device, while the server has none.

**Also not reset:** other device state (B-12) and RevenueCat's configured user id (B-21).

**And:** without a backend, or offline, `getSupabase()`/`getUser()` fails and deletion returns
"something went wrong" — a local-only user cannot erase local data at all.

**Fix.** Add `clear()` to the store and call it; reset every device store through one
`eraseDevice()` function with a test that lists all `nearby.*` keys and fails when a new one is
not covered; allow a local wipe when there is no server account.

### B-06 · `session_start` is never recorded — *High · Read*

**Where:** `App.tsx:495-497` with `components/useTracker.ts:21-33`.

The effect fires once at mount. Consent is read through a ref that still holds the all-off
default, because the stored consent loads asynchronously (`App.tsx:541-556`). The consent gate
drops the event. Nothing fires it again: not when consent loads, and not when the app returns
from the background, which on Android is how most "opens" happen.

**Effect.** `docs/launch/DASHBOARDS.md` builds day-7 return (the primary go/kill metric), the
onboarding funnel, weekly retention, active people and catch taste on `session_start`. All read
zero. The first `this_week_opened` of a launch races the same load.

**Fix.** Fire `session_start` when consent has loaded and on every `AppState` change to `active`
(with a 30-minute session window). Add an App-level test with stored consent that asserts the
event is delivered.

### B-07 · No way to sign back in with a linked email — *High · Read*

**Where:** `lib/accountLinking.ts:80` (`updateUser({ email })`) is the only auth call besides
anonymous sign-in. There is no `signInWithOtp`, `verifyOtp` or password flow anywhere, and the
app handles no deep link (`detectSessionInUrl: false`, the `nearby://` scheme is unused).

**Effect.** After a reinstall or on a second phone the user gets a new anonymous account and has
no screen on which to enter the email. The promise in `link.body`, in T-133 and in the privacy
policy ("to keep it across reinstalls/devices") cannot be kept. The confirmation link itself
lands on the Supabase Site URL, which also needs checking (**Needs live check**).

**Fix.** Add "I already have an account" (onboarding and Settings): email → 6-digit code
(`signInWithOtp` + `verifyOtp`, no deep link needed) → replace the anonymous session → pull the
collection (needs B-11) → `Purchases.logIn` with the restored id (B-21).

## 8. Product observations

1. **The thesis was passed on judgement, not data.** The gate (T-041) records a Director GO
   ahead of the field test (T-038–T-040). With B-06 fixed, the Play closed test can be that test:
   the pre-registered thresholds in `VALIDATION-CRITERIA.md` still apply and cost nothing to
   check.
2. **Spotted is one tap, and This Week offers fifty.** A user can "collect" fifty species in a
   minute. That is the hollow path the thesis worries about. Options: let the daily notification
   be the main way a species is first met, cap first-time spots from the list per day, or lean on
   F-07 so that a sighting carries something of the user's own.
3. **The paid trigger is rare by design.** Catching needs a walk to a spot, so few people will
   use three catches in a season, and the paywall is the only sales signal. The Full Game also
   holds bird song and offline play; say so where people decide (I-30) and consider one more
   honest, visible benefit before relying on conversion numbers. B-01 currently distorts the
   funnel in the other direction.
4. **County packs sell permission to tap.** Outside the home county a pack buys spotting and
   catching; previewing is free. For a traveller that is thin. The all-Sweden pass at 99 SEK is
   the clearer offer; watch whether single counties sell at all.
5. **Android only.** Sweden is an iPhone-heavy market. Every other growth idea is capped until
   T-001 is done.
6. **Launch season.** A first run in November–February meets the quietest lists of the year and,
   with B-04, lists that are wrong. Fix B-04, add F-21, and aim marketing at March–April.
7. **Content at scale without review** is a deliberate decision (T-177). It needs its
   counterweight: I-32 and I-33.
8. **Cost.** Storage is inside the free tier (391 MB of 1 GB when last measured, at 6,825
   species; worth re-measuring at 8,064 with thumbnails and sounds). Egress is the limit that
   will be hit first (B-20), followed by the sender's run time (B-51).

## Appendix A — Reproducing B-01

With the two migrations `20260704000001_profiles_and_collection.sql` and
`20261029000001_free_catch_enforcement.sql` applied to an empty Postgres (plus a stub
`auth.users` table and the three roles), run the statement PostgREST sends for an upsert four
times for one user and one species:

```sql
insert into public.collection
  (user_id, species_id, spotted_at, caught_at, helped_at, helped_kind, prime_bonus)
values ($1, 'a', $2, $3, $4, $5, false)
on conflict (user_id, species_id) do update set
  spotted_at = excluded.spotted_at, caught_at = excluded.caught_at,
  helped_at = excluded.helped_at, helped_kind = excluded.helped_kind,
  prime_bonus = excluded.prime_bonus;
```

1. spotted only → no profile row yet
2. spotted + caught → `free_catches_used = 2`
3. spotted + caught + helped → `3`
4. the same row again → `ERROR: free_catch_limit`
